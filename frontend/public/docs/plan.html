4.2 Widget registry: single source of truth DONE — 6/6

Each widget is declared once on the back, in backend/src/widgets/registry.ts. An entry contains service, name, description, params (with type: 'string' | 'integer'), a Zod schema, and fetch(config, ctx).

From this registry: we generate /about.json, validate configs on create/reconfigure, and serve GET /api/v1/widgets to the front. No more hard-coded catalog.ts or params_schema column in the DB — Strategy/Adapter pattern, without duplication.

Finding (historical audit note, later completed): the compiled registry (backend/dist/widgets/registry.js) once held only the 3 “B” widgets (precipitation_forecast, security_alerts, feed_summary). The 3 “A” widgets were an explicit TODO in the file — later completed (see §0 / §5).

4.3 Timer DONE

The Timer is centralized on the client; the cache is on the server:

  1. On dashboard load, each instance registers with the client Timer with its refresh_rate (min 30 s).
  2. When due, the Timer calls GET /api/v1/dashboard/widgets/:id/data.
  3. The API returns the cache if younger than refresh_rate seconds, otherwise calls the adapter and stores the result in widget_cache.
  4. The API updates last_refreshed_at and status; the front displays them.

Finding: compiled dashboard.routes.js exposes GET /widgets/:id/data with this cache logic — matches the design. A server worker (BullMQ) remains a possible evolution after 01/10.

10. Technical pitfalls

These pitfalls only show up at the end of integration; we address them from the start.

  1. /about.json swallowed by the SPA. Without a dedicated nginx rule, try_files returns index.html. Provide an exact location, before the general rule. 
    location = /about.json { proxy_pass http://api:3000; }
location /api/  { proxy_pass http://api:3000; }
location /  { root /usr/share/nginx/html; try_files $uri /index.html; }
  2. client.host = nginx IP. Requires app.set('trust proxy', 1) — already done in app.js.
  3. SameSite=Strict cookie and OAuth. Use SameSite=Lax for the session cookie, otherwise the return from github.com loses the session.
  4. Link GitHub to the right user. The state must be random, stored server-side with the user_id and a short expiry.
  5. OAuth callback URL. Declare http://localhost:8080/api/v1/auth/oauth/github/callback, secrets only in .env.
  6. Migrations on startup. The API must run Drizzle migrations then the admin seed before listening; Postgres healthcheck + depends_on: condition: service_healthy.
  7. Confirmation emails. SMTP to internal mailpit:1025, but the confirmation flow uses a 6-digit OTP code (entered in the app), not only a magic link — UI still lives at http://localhost:8080.
  8. GitHub rate limit. Without a token, 60 requests/hour. Always go through the user token + cache.

4.3 Timer FAIT

Le Timer est centralisé côté client, le cache côté serveur :

  1. Au chargement du dashboard, chaque instance s'enregistre auprès du Timer client avec son refresh_rate (min 30 s).
  2. À l'échéance, le Timer appelle GET /api/v1/dashboard/widgets/:id/data.
  3. L'API renvoie le cache s'il a moins de refresh_rate secondes, sinon appelle l'adapter et stocke le résultat dans widget_cache.
  4. L'API met à jour last_refreshed_at et status ; le front les affiche.

Constat : dashboard.routes.js compilé expose bien GET /widgets/:id/data avec cette logique de cache — conforme au design. Un worker serveur (BullMQ) reste une évolution possible après le 01/10.

10. Pièges techniques

Ces pièges ne se voient qu'en fin d'intégration ; on les traite dès le départ.

  1. /about.json avalé par le SPA. Sans règle nginx dédiée, try_files renvoie index.html. Prévoir une location exacte, avant la règle générale. 
    location = /about.json { proxy_pass http://api:3000; }
location /api/  { proxy_pass http://api:3000; }
location /  { root /usr/share/nginx/html; try_files $uri /index.html; }
  2. client.host = IP de nginx. Nécessite app.set('trust proxy', 1) — déjà fait dans app.js.
  3. Cookie SameSite=Strict et OAuth. Utiliser SameSite=Lax pour le cookie de session, sinon le retour de github.com perd la session.
  4. Lier GitHub au bon utilisateur. Le state doit être aléatoire, stocké côté serveur avec le user_id et une expiration courte.
  5. URL de callback OAuth. Déclarer http://localhost:8080/api/v1/auth/oauth/github/callback, secrets uniquement dans .env.
  6. Migrations au démarrage. L'API doit lancer les migrations Drizzle puis le seed admin avant d'écouter ; healthcheck Postgres + depends_on: condition: service_healthy.
  7. Mails de confirmation. SMTP vers mailpit:1025 en interne, mais le lien de confirmation doit pointer vers http://localhost:8080.
  8. Rate limit GitHub. Sans token, 60 requêtes/heure. Toujours passer par le token utilisateur + cache.
