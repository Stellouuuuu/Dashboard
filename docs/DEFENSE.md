## 1. Starting the project

- `docker-compose.yml` (repo root) defines 4 services: `nginx`, `api`, `postgres`, `mailpit`.
- `nginx` publishes **port 8080** (`docker-compose.yml:11`, `"8080:80"`) and serves the built SPA, proxying `/api/*` and `/about.json` to `api` (`nginx/nginx.conf`).
- No manual step is required: `JWT_SECRET` and `CRYPTO_KEY` are auto-generated on first boot by `backend/src/config/secrets.ts` and persisted in the `api_secrets` Docker volume (mounted at `/data/secrets`, see `docker-compose.yml:39`). The demo admin account is seeded by `backend/src/db/seed-admin.ts`, run from `backend/src/server.ts:7` before the server starts listening.
- Startup order is enforced by `depends_on` + a Postgres healthcheck (`docker-compose.yml:40-44`, `pg_isready`), so `api` waits for `postgres` to actually be ready, not just started.

## 2. `/about.json`

- Route: `GET /about.json` → `backend/src/modules/about/about.routes.ts` → `getAbout` in `backend/src/modules/about/about.controller.ts`.
- `client.host` comes from `req.ip`, which requires `app.set("trust proxy", 1)` in `backend/src/app.ts:17` - without it, behind nginx, `req.ip` would be the proxy's address instead of the client's.
- `server.current_time` is `Math.floor(Date.now() / 1000)` - Unix seconds (`about.controller.ts:26`).
- `server.services[]` is generated by grouping `listWidgetDefinitions()` from the registry by `service` (`about.controller.ts:12-21`) - nothing here is hand-written; adding a widget to the registry automatically updates this endpoint.
- Param types exposed are only `"string"` and `"integer"` (`WidgetParam["type"]`, `backend/src/widgets/registry.ts:10`).

## 3. Accounts

- Registration: `POST /api/v1/auth/register` (`auth.routes.ts:22`) → `auth.service.ts:register` - password hashed with **bcrypt, cost 12** (`auth.service.ts:58`), account created with `emailConfirmed: false` (`db/schema.ts:21`), then a 6-digit OTP is emailed.
- Verification: OTP is a random 6-digit code (`lib/token.ts:generateOtpCode`, `randomInt` padded to 6 digits), valid **15 minutes** (`auth.service.ts:12`, `OTP_TTL_MS`), stored **hashed with SHA-256** in `email_tokens.token_hash` (`lib/token.ts:hashToken`, `db/schema.ts:28-34`) - never in clear text.
- Login: `POST /api/v1/auth/login` requires a confirmed, non-suspended account (`auth.service.ts:121-123`) and returns two httpOnly cookies (`auth.controller.ts:16-34`): `access_token` (JWT, 15 min) and `refresh_token` (opaque random token, 30 days, path-scoped to `/api/v1/auth`).
- Password/token readability: passwords are never stored in clear (bcrypt hash only, `users.password_hash`); refresh tokens and OTP codes are stored as SHA-256 hashes, never raw; OAuth access tokens are stored AES-256-GCM encrypted (`oauth_accounts.access_token`, see §5). Nothing is logged in clear either - `error.middleware.ts:10` logs the error object, not tokens.
- External accounts: GitHub is connected via OAuth 2.0 **for the currently logged-in user** - the link flow requires `requireAuth` on `GET /api/v1/auth/oauth/github` (`auth.routes.ts:36`) and the state JWT carries `sub: userId` (`github-oauth.service.ts:49-53`), so the callback (which itself has no session, see §5) always links to the account that started the flow.

## 4. Services and widgets

- **5 services**, **10 widgets** - 2 per service - all declared in the single registry `backend/src/widgets/registry.ts:47-184`:

  | Service | Widgets |
  | --- | --- |
  | `weather` | `city_temperature`, `precipitation_forecast` |
  | `github` | `security_alerts`, `recent_commits` |
  | `rss` | `feed_summary`, `article_list` |
  | `finance` | `exchange_rate`, `crypto_price` |
  | `hackernews` | `top_stories`, `story_search` |

- Usable without a subscription: `weather`, `rss`, `finance`, `hackernews` - `services.service.ts:8-10` only requires OAuth for `github` (`OAUTH_REQUIRED = new Set(["github"])`); the other four are marked `subscribed: true` unconditionally (`services.service.ts:29`).
- Every widget parameter is typed (`"string" | "integer"`, `registry.ts:10`) and validated per-widget with a Zod `schema` (e.g. `precipitation_forecast.days` must be an integer 1–7, `registry.ts:72`; `exchange_rate` currency codes must match `/^[A-Za-z]{3}$/`, `registry.ts:141-142`).
- Two instances of the same widget with different configs give different results at the same time because the config is stored **per instance** in `widget_instances.config` (JSONB, `db/schema.ts:67`) and the per-widget cache key is the **instance id**, not the widget name (`widget_cache.widget_instance_id`, `db/schema.ts:75-76`) - two instances never share a cache row.

### Cross-cutting statuses

- `429` (`RATE_LIMITED`) can happen on any route behind `apiLimiter` (100 req/min/IP, `app.ts:22`); auth routes additionally sit behind `authLimiter` (10 req/min/IP).
- `404` with `code: "NOT_FOUND"` for any unmatched route (`error.middleware.ts:notFoundHandler`).
- `500` with `code: "INTERNAL_ERROR"` is the fallback for any uncaught error (`error.middleware.ts:errorHandler`).

## 9. Where the cache lives

- Storage: Postgres table `widget_cache` (`backend/src/db/schema.ts:74-80`) - primary key `widget_instance_id` (one row per widget **instance**, not per widget type), columns `payload` (JSONB) and `fetched_at`.
- Read/write: `backend/src/modules/dashboard/dashboard.repository.ts` (`getCachedPayload`, `upsertCachedPayload`).
- Freshness check: `dashboard.service.ts:fetchWidgetData` computes `ageSec = (now - fetchedAt) / 1000` and serves the cached payload if `ageSec < instance.refreshRate`; otherwise it calls the widget's adapter, stores the fresh result, and updates `widget_instances.status` (`"ok"`/`"error"`, `dashboard.repository.ts:updateRefreshStatus`).
- Minimum refresh rate: 30 seconds, enforced server-side (`config/constants.ts:REFRESH_RATE_MIN`), independent of what the client asks for.
