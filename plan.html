4.2 Registre de widgets : une seule source de vérité PARTIEL — 3/6

Chaque widget est déclaré une seule fois côté back, dans backend/src/widgets/registry.ts. Une entrée contient service, name, description, params (avec type: 'string' | 'integer'), un schéma Zod, et fetch(config, ctx).

À partir de ce registre : on génère /about.json, on valide les configs à la création/reconfiguration, et on sert GET /api/v1/widgets au front. Plus de catalog.ts codé en dur ni de colonne params_schema en base — pattern Strategy/Adapter, sans duplication.

Constat : le registre compilé (backend/dist/widgets/registry.js) ne contient que les 3 widgets « B » (precipitation_forecast, security_alerts, feed_summary). Les 3 widgets « A » sont un TODO explicite dans le fichier.

4.3 Timer FAIT

Le Timer est centralisé côté client, le cache côté serveur :

  1. Au chargement du dashboard, chaque instance s'enregistre auprès du Timer client avec son refresh_rate (min 30 s).
  2. À l'échéance, le Timer appelle GET /api/v1/dashboard/widgets/:id/data.
  3. L'API renvoie le cache s'il a moins de refresh_rate secondes, sinon appelle l'adapter et stocke le résultat dans widget_cache.
  4. L'API met à jour last_refreshed_at et status ; le front les affiche.

Constat : dashboard.routes.js compilé expose bien GET /widgets/:id/data avec cette logique de cache — conforme au design. Un worker serveur (BullMQ) reste une évolution possible après le 01/10.

10. Pièges techniques

Ces pièges ne se voient qu'en fin d'intégration ; on les traite dès le départ.

  1. /about.json avalé par le SPA. Sans règle nginx dédiée, try_files renvoie index.html. Prévoir une location exacte, avant la règle générale. 
    location = /about.json { proxy_pass http://api:3000; }
location /api/        { proxy_pass http://api:3000; }
location /            { root /usr/share/nginx/html; try_files $uri /index.html; }
  2. client.host = IP de nginx. Nécessite app.set('trust proxy', 1) — déjà fait dans app.js.
  3. Cookie SameSite=Strict et OAuth. Utiliser SameSite=Lax pour le cookie de session, sinon le retour de github.com perd la session.
  4. Lier GitHub au bon utilisateur. Le state doit être aléatoire, stocké côté serveur avec le user_id et une expiration courte.
  5. URL de callback OAuth. Déclarer http://localhost:8080/api/v1/auth/oauth/github/callback, secrets uniquement dans .env.
  6. Migrations au démarrage. L'API doit lancer les migrations Drizzle puis le seed admin avant d'écouter ; healthcheck Postgres + depends_on: condition: service_healthy.
  7. Mails de confirmation. SMTP vers mailpit:1025 en interne, mais le lien de confirmation doit pointer vers http://localhost:8080.
  8. Rate limit GitHub. Sans token, 60 requêtes/heure. Toujours passer par le token utilisateur + cache.
